## 差し込む

[ハーネスからの覚え書き — 利用者の発言ではありません]
**ping が返らないことは、そのホストが停止している証拠になりません。**
ICMP だけを落として稼働し続けているホストは実在します。次の順で確かめてください。

1. **TCP を開いてみる**（これが一次証拠）:
   `timeout 5 bash -c 'exec 3<>/dev/tcp/<IP>/22' && echo open || echo 届かない`
   22 が閉じていても、そのホストらしいポートを試す（3389 / 443 / 445 / 8080 …）。
2. **開いたら挨拶を読む**（応答した動かぬ証拠になる）。**相手が返した行をそのまま貼る**:
   `ssh -v -o BatchMode=yes -o ConnectTimeout=5 <IP> true 2>&1 | grep -i 'remote software'`
   ★挨拶は 8〜24 行目に出ます。**`| head -5` で切らない・`-q` を付けない**（消えます）。
   認証は失敗して構いません。`nc -z -w3 <IP> <ポート>`・`curl -sS -m 5 <URL>` も可。
3. **ARP を見る**（同じ L2 にいるときだけ）: `ip neigh show <IP>` が `REACHABLE` なら生存。
   **別の網なら何も出ないのが正常**で、出ないことは停止の証拠になりません。
4. 「届かない」を1語で潰さない。**refused（相手が拒否）と timeout（応答なし）は別物**です。
   refused ならホストは生きていて、そのポートだけ閉じています。

★報告するときは、**本文の結論と最後の判定行を必ず一致させて**ください。
★**自分のホストの状態**（自分の待ち受けポート・自分のディスクやメモリ）を、
　相手が応答した証拠にしないでください。「開いています」は**あなたの結論**で、
　証拠は**相手が返した行そのもの**です。

## なぜ（人が読む部分・注入されない）

ラボの共有文書に「ping で死活判定してはいけないホスト」として実測が残っている
（Windows VM は ICMP を落とすが 22/3389 は開く・クラウドの一部も ICMP 不可で 22 は開く）。

2026-08-30 の計測で実際に踏んだ: ping 失敗のあと TCP を一度も試さず、
本文には「監視の誤報の可能性が高い」と書きながら判定行に「停止」と書いた。
TCP は同じ機械から実際に開けた（22 と 3389 の両方）。
