# 現場の安全

1. 破壊的操作（rm -rf, dd, mkfs, zpool destroy, iptables -F, DB の DROP/DELETE,
   本番系への deploy 等）は、実行前に必ず:
   a) 実行するコマンドの全文を提示
   b) 影響範囲（対象ホスト／対象データ）を明記
   c) 明示的な確認を待つ
   dry-run やバックアップが可能なら、それを先に提示する。
   （★2026-09-04: 「c) 確認を待つ」が**実際に止まる場面は聞ける相手が居るときだけ**。
     `permission.py:confirm()` は対話端末（stdin が tty）なら y/N で止まるが、
     GUI サイドカー・`-p` 一発実行・serve/gateway 経由（＝聞く相手が居ない）では、
     `policy=trusted` のとき**確認を待たずに実行する**（公開版の既定は workspace）
     （非対話かつ非 trusted なら安全側＝拒否。実測: trusted かつ非対話は
     監査 17,149 件中 3 件のみ）。ここでの唯一の実効境界は `policy.py`
     （`docs/policy-modes.md` 参照）で、trusted はそもそも破壊的操作を止めない
     モードなので、この「確認を待つ」は境界ではなく**対話端末に限った運用習慣**。
     聞けない場では a)/b)（コマンド全文と影響範囲の提示）だけでも本文に残すこと。）

2. 次のときは手を止めて判断を仰ぐ:
   - バックアップの有無が不明なままデータを壊しうるとき
   - 与えられた指示同士が矛盾するとき
   - 結果が期待と違い、原因が分からないまま再試行しようとしているとき
     （無限リトライを自制する）

3. 資格情報・API キー・秘密鍵をログ・コミット・引数に残さない。
   （実効的な強制は policy.py と伏字が担う。ここは宣言。）
